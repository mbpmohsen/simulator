# Python Game Server – API and Runtime Guide

This document describes the server-side API, data models, and runtime behavior for the Python Game Server. It focuses on the HTTP endpoints, WebSocket channels, and how request payloads map to runtime objects. Where applicable, example payloads are provided.

The FastAPI app lives in `server/networking.py`. Core runtime is in `server/game_server.py` and `server/game_logic.py`. Action execution is implemented in `server/Actions.py`. Domain models are in `server/models.py`.

> Note: NE analytics run asynchronously and are not exposed via API; plots are written to `logs/plots/<game_id>/`.

---

## Quick Start

- Start the FastAPI app with Uvicorn (example):
  - Optional: environment and dependency setup based on your environment.
  - The API exposes admin endpoints to configure and start a new game.
- Typical flow:
  1. Configure sides/teams/players/actions via `/admin/configure_all`.
  2. Optionally configure game events or black market items.
  3. Connect players over WebSocket `/ws/{code}`.
  4. Start the game via `/admin/start_game` (or auto-start when all players are connected, depending on your setup).

## Models and Runtime Objects

These reside in `server/models.py` and are important for understanding payload shapes.

- Player
  - name: string – Display name.
  - code: string – Unique code used to connect via WebSocket (`/ws/{code}`). Generated by server when configuring players.
  - team: Team – Assigned at configuration.
  - connected: bool – Set when WebSocket connects.
  - websocket: WebSocket – Runtime reference.
  - vote_weight: float – Weight of the player’s vote.
  - is_leader: bool – Leader flag; you may use it to break ties or show priority in UI.

- Team
  - name: string.
  - side: GameSide – Assigned via `/admin/configure_all` (see “side_assignments”).
  - players: Player[] – Team players list.
  - points: int – Score (updated by actions resolution).
  - credits: float – Team credits (spent by actions and purchases).
  - vulnerabilities: dict[str, list[str]] – Tracks attacker-specific vulnerabilities by action name. Internal.
  - action_probabilities/base/current_*: various dicts – Effective probabilities, costs, and factor caches used during resolution.
  - ne_summary: dict – Asynchronous NE analytics snapshot.

- GameSide
  - name: string.
  - teams: Team[] – Teams assigned to this side.
  - total_credits: float – Shared side credits; actions may affect this.

- BlackMarketItem
  - name: string.
  - item_type: "probability" | "growth" | "cost" | "tech". (whether the item affects probability/growth/cost/tech factor, for example and item of multiply effect_type and growth item_type, would multiply the growth of the target action by the provided value)
  - effect_type: "increase" (addition by value) | "decrease" (subtraction by value) | "multiply" (multiplication by value).
  - value: float – Magnitude (meaning depends on effect_type/item_type).
  - target_action: string – Action name affected.
  - duration: int – Number of turns.
  - cost: float – Credit cost.

- GameEvent (More explanation is provided in the endpoint section of readme)
  - name: string.
  - effect_type: "probability" | "growth" | "cost" | "limit" | "tech".
  - target_action: string | "all" – Which action the event affects.
  - target_action_type: "attack" | "defense" | "both".
  - value: float – Magnitude (meaning depends on effect/modifier).
  - start_turn: int – First turn the event is active.
  - duration: int – How many turns the event lasts.
  - modifier_type: "increase" | "decrease" | "multiply" – How `value` modifies the base attribute.
  - affected_sides: string[] – If provided, restrict the event to those sides; empty or missing means all sides.
  - limit_type: Optional string – For effect_type "limit" (e.g., "disable_attack", "disable_defense", or other future limits).
  - limit_value: Optional float – Optional numeric parameter for limits.

## WebSocket Endpoints

- `GET /ws/{code}` – Player connection channel
  - Path parameter `code` is the player’s unique code (generated during configuration).
  - The server pushes instructions and receives player input (votes, etc.).
  - When a player connects, their `Player.connected` becomes true and they start receiving server updates.

- `GET /ws/game-info` – Admin/observer info channel
  - Streams game info (host, port, turns, point threshold, sides, teams, and basic team state).
  - Does not expose sensitive analytics (no NE details).

## HTTP Admin Endpoints

Implementation: `server/networking.py`

- `GET /admin/start_game` – Start game
  - Kicks off the game loop if a game is configured and players are connected.
  - Response: `{ "detail": "..." }` on success/failure.

- `POST /admin/configure_all` – Configure everything in a single call
  - Body model: `ConfigureAllRequest`
  - Fields:
    - side_names: string[] – Names of sides (e.g., ["Red", "Blue"]).
    - team_names: string[] – Team names (e.g., ["Team1", "Team2"]).
    - num_turns: int – Total number of turns for the game; must be > 0.
    - teams_and_players: object – Map of team name → array of player configs.
      - PlayerConfig: { name: string, is_leader?: bool, vote_weight?: float }
      - Server generates a unique `code` per player.
    - side_assignments: object – Map team → side name. Each team must exist and each side must be defined in `side_names`.
    - point_threshold: int – The points required to win. Must be > 0.
    - actions: object – Game actions config:
      - attack: object – Map action name → ActionConfig.
      - defense: object – Map action name → ActionConfig.
      - ActionConfig fields:
        - probability: float – Base success probability (0–100); events and black market modify this.
        - counter_actions: string – For defense entries, which attack this defense counters. For attack entries, which defense counters it.
        - growth: float – Growth factor; a number added to action on probability on success.
        - tech: float – tech factor; a number added to action probability on success.
        - cost: float – Credit cost for the action.
    - team_growth_factors: object – Per-team growth multipliers:
      - Structure: team → { attack: { action_name: float }, defense: { action_name: float } }
      - Used by growth factor computations in both attack and defense.
    - team_tech_factors: object | null – Per-team tech multipliers (same structure as growth):
      - Optional; if omitted or null, tech defaults to neutral.
    - side_credits: object – Initial credits per side name.
    - black_market_items: BlackMarketItemConfig[] – Store/global items available for purchase:
      - Fields: { name, item_type, effect_type, target_action, target_action_type, value, duration, cost }

  - Effects on runtime:
    - Initializes `GameServer` with sides, teams, players, and actions.
    - Assigns teams to sides and gives sides initial credits.
    - Preloads black market inventory.

  - Example:
    ```json
    {
      "side_names": ["Red", "Blue"],
      "team_names": ["Team1", "Team2"],
      "num_turns": 10,
      "teams_and_players": {
        "Team1": [
          {"name": "Player1", "is_leader": true, "vote_weight": 2.0},
          {"name": "Player2"}
        ],
        "Team2": [
          {"name": "Player3", "is_leader": true},
          {"name": "Player4"}
        ]
      },
      "side_assignments": {"Team1": "Red", "Team2": "Blue"},
      "point_threshold": 5,
      "actions": {
        "attack": {
          "DDOS": {"probability": 90, "counter_actions": "DDOS_DEFENSE", "cost": 10.0},
          "SQL_INJECTION": {"probability": 40, "counter_actions": "SQL_INJECTION_DEFENSE", "cost": 15.0}
        },
        "defense": {
          "DDOS_DEFENSE": {"probability": 90, "counter_actions": "DDOS", "cost": 8.0},
          "SQL_INJECTION_DEFENSE": {"probability": 40, "counter_actions": "SQL_INJECTION", "cost": 12.0}
        }
      },
      "team_growth_factors": {
        "Team1": {"attack": {"DDOS": 2.0}, "defense": {"DDOS_DEFENSE": 1.5}},
        "Team2": {"attack": {"SQL_INJECTION": 2.0}, "defense": {"SQL_INJECTION_DEFENSE": 1.5}}
      },
      "team_tech_factors": {
        "Team1": {"attack": {"DDOS": 1.2}, "defense": {"DDOS_DEFENSE": 1.1}},
        "Team2": {"attack": {"SQL_INJECTION": 1.3}, "defense": {"SQL_INJECTION_DEFENSE": 1.2}}
      },
      "side_credits": {"Red": 100.0, "Blue": 100.0},
      "black_market_items": [
        {"name": "Attack Booster", "item_type": "probability", "effect_type": "increase", "target_action": "DDOS", "target_action_type": "attack", "value": 20.0, "duration": 3, "cost": 25.0},
        {"name": "Growth Enhancer", "item_type": "growth", "effect_type": "multiply", "target_action": "SQL_INJECTION", "target_action_type": "attack", "value": 2.0, "duration": 2, "cost": 30.0}
      ]
    }
    ```

- `POST /admin/configure_events` – Replace existing events with a new list
  - Body model: `ConfigureEventsRequest` with `events: GameEventConfig[]`.
  - GameEventConfig fields:
    - name: string – Unique name for the event.
    - effect_type: "probability" | "growth" | "cost" | "limit" | "tech". (this field indicates that what part of the action does the event affect, it can affect probability/growth/cost/tech or limit a specifig action for a duration).
    - target_action: string | "all" – A specific action or "all".
    - target_action_type: "attack" | "defense" | "both".
    - value: float – Magnitude; see modifiers below.
    - start_turn: int – First turn included (inclusive).
    - duration: int – Number of turns the event spans.
    - modifier_type: "increase" (addition by value) | "decrease" (subtraction by valye) | "multiply" (multiplication by value) – How `value` changes the base. 
    - affected_sides: string[] | null – Limit scope to specific sides; empty = all sides.
    - limit_type: Optional string – For limits (e.g., "disable_attack" or "disable_defense").

  - Semantics:
    - probability/growth/cost/tech: `modifier_type` applies `value` onto the base attribute.
      - increase/decrease: additive delta (e.g., +10 probability points).
      - multiply: multiplicative factor (e.g., x1.5 on growth).
    - limit: Enforces a rule. If `limit_type` is "disable_attack", attacks are disabled while active (for the targeted scope/actions).

  - Example:
    ```json
    {
      "events": [
        {
          "name": "Security Lockdown",
          "effect_type": "limit",
          "target_action": "all",
          "target_action_type": "attack",
          "value": 0,
          "start_turn": 6,
          "duration": 1,
          "modifier_type": "increase",
          "affected_sides": [],
          "limit_type": "disable_attack",
          "limit_value": null
        },
        {
          "name": "Growth Surge",
          "effect_type": "growth",
          "target_action": "DDOS",
          "target_action_type": "attack",
          "value": 1.5,
          "start_turn": 5,
          "duration": 2,
          "modifier_type": "multiply",
          "affected_sides": ["Red"],
          "limit_type": null,
          "limit_value": null
        }
      ]
    }
    ```

- `POST /admin/add_events` – Append events to the existing set
  - Same body as configure_events; existing events remain, and new ones are added.

- `DELETE /admin/delete_event/{event_name}` – Remove a specific event by name

- `DELETE /admin/clear_events` – Remove all events

- `GET /admin/get_current_events` – Retrieve current stored events

## Action Execution Semantics (server/Actions.py)

- AttackAction
  - Validates target and side legality.
  - Checks event-based action limits (e.g., disable_attack).
  - Computes effective cost and probability (after applying events, growth/tech factors, black market effects).
  - Deducts credits if sufficient.
  - Success path:
    - Awards 1 point.
    - Applies growth/tech factor progress effects into the team’s factor state.
    - Marks target vulnerable to this attacker for this action, increasing future success.
  - Failure path: records action outcome.

- DefenseAction
  - Similar checks for limits and costs.
  - When successful against a vulnerability, reduces opponent pressure (reflected in future turns’ probabilities) and clears vulnerabilities (attacker-specific).

- BlackMarketAction
  - Applies item effects in-memory immediately (probability/growth/cost/tech effects) with turn-bounded duration.

All actions record a detailed snapshot via `record_detailed_action` for auditing.

## Game Lifecycle (server/game_logic.py)

- `GameController.start_game()` runs the game loop for `num_turns` or until `point_threshold` is met.
- Per turn:
  1. Update active effects and turn-timed events.
  2. Notify players about events.
  3. Collect votes from connected players within `VOTE_TIMEOUT`.
  4. Resolve purchases and actions.
  5. Update and persist turn state (credits, points, vulnerabilities, effects).
  6. Kick off async NE analytics for the new state (results stored server-side for admin purposes).
- At end, `display_final_scores()` and mark the game as `finished`.

---

## Field Reference and Constraints

- Probabilities are expressed as percentages (0–100). Internally converted to 0–1 when evaluating success.
- Costs and credits are floating-point; ensure your payload uses numbers (not strings).
- Events with `limit_type` override action availability irrespective of probabilities.
- Team/Side names are case-sensitive in mapping objects.

---

## Tips and Common Pitfalls

- Always configure `side_names`, `team_names`, `side_assignments`, and `actions` coherently—undefined teams or sides in mappings will cause validation or runtime errors.
- Provide `num_turns > 0` and `point_threshold > 0`.
- Ensure players use their generated codes to connect via `/ws/{code}` before starting the game.
- Use `configure_events` to reset and `add_events` to append; both accept the same payload shape.
- Black market inventory is configured via `/admin/configure_all` and becomes available in-game; players vote to purchase via the game’s turn flow.

## Configuration (config.yml)

Location: project root `config.yml` (loaded by `server/config_loader.py` during startup). These settings influence bindings, timing, client liveness, persistence, logging, and NE analytics/plots.

Values below reflect the defaults provided in the attached config.

### network
- host: string (Default: "0.0.0.0")
  - Interface the FastAPI server binds to. Use "0.0.0.0" to listen on all interfaces; use "127.0.0.1" to bind locally only.
- port: int (Default: 8000)
  - TCP port for the HTTP/WebSocket server.

Effect: Controls where the API and WebSockets are reachable. If running in Docker, ensure ports are exposed in compose.

### game
- turn_duration: int seconds (Default: 60)
  - Length of a turn. Governs pacing and deadlines for actions/purchases.
- vote_timeout: int seconds (Default: 60)
  - Max time to wait for player votes in a turn. If less than `turn_duration`, vote collection can close early; if greater, it’s effectively capped by `turn_duration`.
- default_point_threshold: int (Default: 5)
  - Win condition when not provided in `/admin/configure_all` (request `point_threshold` takes precedence).
- info_interval: int seconds (Default: 5)
  - Interval for streaming summary info on `/ws/game-info`.

Effect: Tunes the game loop in `server/game_logic.py` (turn cadence, vote windows, broadcast frequency).

### client
- ping_interval: int seconds (Default: 20)
  - Interval between pings to clients to verify connectivity.
- pong_timeout: int seconds (Default: 60)
  - How long the server waits for a pong/response before considering a client unresponsive.
- heartbeat_interval: int seconds (Default: 30)
  - Interval for periodic heartbeat messages.
- heartbeat_timeout: int seconds (Default: 30)
  - Grace window for missing heartbeats before marking a client as disconnected.

Effect: Used by heartbeat/liveness logic to keep player sessions healthy and drop stale connections.

### database
- host: string (Default: "mongodb")
  - MongoDB host (service name if using Docker Compose).
- port: int (Default: 27017)
  - MongoDB port.
- name: string (Default: "game_db")
  - Database name used by the server.

Effect: Consumed by `server/db_manager.py` for persisting game state, events, and action records. In Docker, the host typically matches the service name in `compose.yml`.

### logging
- level: "DEBUG" | "INFO" | "WARNING" | "ERROR" | "CRITICAL" (Default: "DEBUG")
  - Root logger level.
- format: string (Default: "%(asctime)s | %(levelname)-8s | %(name)s | %(message)s")
  - Formatter for human-readable logs.
- datefmt: string (Default: "%H:%M:%S")
  - Timestamp format.
- noisy_level: string (Default: "INFO")
  - Level applied to noisy third‑party loggers to reduce verbosity.
- json: bool (Default: false)
  - Emit JSON logs (console becomes JSON too). Prefer true for structured log collectors.
- color_console: bool (Default: false)
  - If true and not JSON, colorizes console logs.
- color_file: bool (Default: true)
  - Writes an ANSI‑colored rotating text log for humans (see `logging_config.py`).
- color_file_name: string (Default: "logs.log")
  - Filename within the `logs/` directory for the colored log.

Effect: Wired up by `server/logging_config.py`. Use JSON for production pipelines; use colorized text for local debugging.

### ne (Nash/analytics)
#### since we removed SAS from latest calculation and we are only workinng with payoff matrix and EV, fields relating to SAS are not used currently, though the value is calculated but its not used anywhere.

- discount_gamma: float (Default: 0.85)
  - Discount factor used when valuing future payoffs/progress. Lower values emphasize immediate rewards.
- ev_weight: float (Default: 0.6) (not used!)
  - Weight of expected value in the SAS/score composite.
- progress_weight: float (Default: 0.4) (not used!)
  - Weight of progress (growth/tech/vulnerability progress) in the SAS/score composite.
  - Note: Typically `ev_weight + progress_weight = 1.0`, but the system uses provided values as-is.
- progress_cap: float (Default: 1.0)
  - Clamps progress contribution so it doesn’t dominate the composite score.
- ev_floor: float (Default: 0.0)
  - Minimum contribution from EV to avoid negative or negligible values zeroing out strategy comparison.
- probability_scale: float (Default: 100.0)
  - Converts percentage probabilities into [0,1] space. Don’t change unless your inputs aren’t in percent.
- eff_inc_q_cap: float (Default: 0.9999)
  - If a success probability q ≥ cap, additional efficiency increases are ignored to prevent overflow.

### log related configurations of NE 

- debug_max_detail_logs: int (Default: 12)
  - Maximum number of detailed payoff/matrix debug entries per turn when detailed logging is enabled.
- debug_round_decimals: int (Default: 4)
  - Rounding applied in debug signatures to reduce noisy diffs.
- log_per_target: bool (Default: true)
  - Emit per‑target analytics JSON lines. Note: In the current build, detailed per‑target text logs may be disabled in favor of plots; this flag may have limited effect.
- log_matrices: bool (Default: true)
  - Include Ui/Uj matrices in analytics logs (very verbose). Note: Matrix text logs may be disabled; prefer plots.
- plot_matrices: bool (Default: true)
  - Save per‑turn numeric table images for Ui/Uj and team EVs under `plot_dir/<game_id>/`.
- plot_dir: string (Default: "logs/plots")
  - Base directory for saved NE plots.

Effect: These govern NE analytics generation and output. If plots are enabled, you’ll see four vertically stacked tables per turn: Team1 vs Team2 payoff matrix, Team2 vs Team1 payoff matrix, Team1 expected value, Team2 expected value, with wrapped labels and tight layout.
